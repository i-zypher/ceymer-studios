The thesis

Can an LLM be a disciplined trader?

The question driving Ceymer Trading isn't "can AI predict the market" — that's the wrong question. The right question is: given good market data, well-defined modes, and strict risk parameters, can an LLM make consistent, rule-following trading decisions that a human discretionary trader would struggle to replicate?

The terminal is the experimental apparatus for that question. Three Alpaca accounts run in parallel — two paper-trading environments and one live — so I can compare strategies against themselves and against the market in real time.

The modes

Six personalities, one brain.

The Claude Haiku engine operates in one of six modes at any time, each with its own risk profile, sector bias, and decision framework:

01
Conservative
Capital preservation. Slow, deliberate entries. Heavy diversification.
02
Balanced
The default. Moderate risk, blended momentum and value signals.
03
Aggressive
Higher conviction, larger positions. Will lean into momentum.
04
Momentum
Pure trend-following. Rides what's moving, exits what isn't.
05
Contrarian
Buys weakness, sells strength. Tests the mean-reversion hypothesis.
06
Pause
Hold cash. No new positions. Used during high-uncertainty periods.
Architecture

How it actually runs.

scheduler.ts · cloud function v2 · node 24 
// Triggered every 10 min during market hours
export const tradingBrain = onSchedule({
  schedule: "every 10 minutes",
  timeZone: "America/New_York",
}, async (event) => {
  if (!isMarketOpen()) return;

  const accounts = ["paper", "paper2", "live"];

  for (const account of accounts) {
    const ctx = await buildMarketContext(account);
    const decision = await claudeHaiku.decide(ctx);
    await alpaca.execute(account, decision);
    await firestore.log('ceymer-trading', decision);
  }
});

Three pieces: a market context builder that gathers positions, recent fills, and price action; the Haiku brain that interprets context and emits a structured decision; and an Alpaca executor that carries it out. All decisions log to a Firestore database with a non-default ID — a small thing that nearly broke the build.

The build · Real talk

Three war stories from the live build.

War story · 01

The Firestore non-default ID trap

The Firestore database for Ceymer Trading uses a non-default ID: ceymer-trading. That's a perfectly valid choice — Firebase supports it — but the Firebase SDK defaults to the default database, silently, every time, in every code path you don't explicitly override.

The fix is two lines that absolutely must be present everywhere: getFirestore(app, 'ceymer-trading') in the modular SDK, and the equivalent explicit database ID in the Admin SDK. Forget either one and your writes go into a phantom default database you'll spend a confused hour trying to find.

War story · 02

PDT and minimum order size on the live account

Going live with a small account immediately surfaced two regulatory realities I'd never had to think about in paper trading: Pattern Day Trader rules and minimum order sizes. The system was issuing decisions that paper would cheerfully execute and live would reject — too small, too frequent, wrong account class.

Both got patched into the executor as pre-flight checks: any decision that would trigger PDT or fall below minimum order size gets logged, skipped, and the brain gets re-prompted with the constraint. The brain learns to size up or sit out.

War story · 03

Cost discipline at 10-minute intervals

Running Haiku every 10 minutes across three accounts during all 6.5 hours of US market hours is roughly 117 API calls per day. That's manageable, but it adds up over a month, and only if every call is doing real work.

The context builder does aggressive caching of anything that doesn't change minute-to-minute (account metadata, sector classifications, holiday calendars), so each prompt is lean and cost-efficient.
